# Research: persistent AI NPC communities for Matrix

Status: proposed research direction, 2026-09-23. This note records source findings and a testable design. It does not report a Matrix implementation or a reproduced result.

## Product question

Can Matrix support a persistent community of distinct AI residents that learn reusable skills, leave useful artifacts in the world, interact with one another and people, and remain inspectable and playable on PC and, later, Quest 3? The first answer should come from an isolated simulation fixture with measured baselines. Existing [Matrix NPC roadmap #29](https://github.com/School-of-the-Ancients/matrix-loading-operator/issues/29) owns reusable character/runtime implementation. School may later use these capabilities for inhabited exhibits, while School retains mentors, lessons, and learner records.

A separate proposed authoring workflow uses Astra to draft a **stick-figure pose sequence** with frame times, contacts and intended root displacement; an artist or Blender workflow then builds, bakes and reviews the animation before Unity import. This is a user-supplied technique to test on one motion. It does not make model output an authoritative animation asset or bypass the rig, license and runtime acceptance in Matrix #14.

A user-shared StarCraft II demonstration describes **one strategic Astra plan before combat, then a Jev selector for each squad/key unit roughly twice per second** (attributed to [@GZhan57](https://x.com/GZhan57); an exact primary post, code and run data were not verified). The transferable hypothesis is a slower planner over faster bounded tactical choices. For Matrix, compare event-driven/scripted selection, one shared controller, and per-resident Jev selectors on the same replay. Report plan staleness, decision delay, invalid actions, cost and call rate as resident count grows; a two-per-second rate is an experiment parameter, not a target requirement. The world executor remains authoritative and falls back when a decision is late or unavailable.

## Proposed resident loop

1. **Observe:** A resident receives only local, permitted facts and an event/receipt history. Separate verified events from beliefs and memories.
2. **Choose a goal:** Needs, personality, schedules and authored constraints produce candidate goals, using existing [Matrix #17](https://github.com/School-of-the-Ancients/matrix-loading-operator/issues/17). Optional model deliberation can propose goals under [Matrix #18](https://github.com/School-of-the-Ancients/matrix-loading-operator/issues/18).
3. **Select a legal action or skill:** The runtime supplies a typed candidate set. Utility/scripted choice is the baseline; Jev is an experiment for one narrow selector. GOAP can expand a chosen goal into bounded steps under [Matrix #16](https://github.com/School-of-the-Ancients/matrix-loading-operator/issues/16).
4. **Execute and verify:** [Matrix #13](https://github.com/School-of-the-Ancients/matrix-loading-operator/issues/13) owns finite execution, cancellation, authored-versus-observed state and outcomes. World state changes only after an accepted action and observed receipt. A failed skill stays failed, even if a model says it succeeded.
5. **Learn and share:** Update personal episode/skill records. Permit a validated, versioned artifact to be advertised in-world, discovered through local observation, used by another resident, and linked to its parent/creator and test evidence. [Matrix #19](https://github.com/School-of-the-Ancients/matrix-loading-operator/issues/19) handles reservations and social actions; [Matrix #20](https://github.com/School-of-the-Ancients/matrix-loading-operator/issues/20) handles persistence, inspection, replay and measured budgets.

Human players can observe and interact through Matrix's supported controls. The [current client API](https://github.com/School-of-the-Ancients/matrix-loading-operator/blob/main/Docs/Client-API-v1.md) uses reviewed proposals for scene changes. NPC simulation needs its own explicit capability and authority contract before autonomous changes are accepted; this research note does not grant a client write access. School lessons and learner data remain School-owned. No agent may turn an artifact into arbitrary downloaded C#/DLL/JavaScript execution.

## Minimal records for an isolated fixture

- **Resident:** stable ID, authored traits, current needs/goal, bounded memory pointers, permitted actions, home/availability, model/policy version.
- **Observation:** tick, source, local visibility, verified world facts, unverified beliefs, prior receipts.
- **Skill:** ID/version, typed preconditions, declarative steps using approved capabilities, expected observations, observed success/failure counts, author and provenance.
- **Artifact:** ID/version, world location, type, creator/parent lineage, inspected properties, bounded behavior payload or data, validator result and reuse events.
- **Outcome:** action ID, actor, tick, accepted/rejected/cancelled status, observed effects, resource costs, source policy and replay seed.

Use a deterministic fixture first. A visual avatar, networked multiplayer, MR room understanding, complex physics, and live model access are separate acceptance steps.

## Evaluation and implementation sequence

1. [Research issue #14](https://github.com/School-of-the-Ancients/school-of-the-ancients-roadmap/issues/14): reproduce a small SwarmWorld scenario, then compare scripted, isolated personal-skill, and shared-artifact policies under the same world rules, seeds, observation limits and budgets. Record raw traces, artifacts, valid reuse, task success, invalid actions, latency and cost. Test whether shared culture improves anything beyond more independent trials.
2. Define the smallest Matrix fixture for [#29](https://github.com/School-of-the-Ancients/matrix-loading-operator/issues/29): two residents, one discoverable and validated artifact, one object interaction, one conflicting resource, save/restore and replay. Use existing [GOAP next-step notes](https://github.com/School-of-the-Ancients/matrix-loading-operator/blob/main/Docs/GOAP-Next-Step.md) and [runtime-behavior limits](https://github.com/School-of-the-Ancients/matrix-loading-operator/blob/main/Docs/Runtime-Behaviors.md); do not assume NPC navigation or general behavior programs already work.
3. [Jev evaluation issue #15](https://github.com/School-of-the-Ancients/school-of-the-ancients-roadmap/issues/15): compare one pre-filtered decision against scripted utility and a generative model on the same saved observations and seeds. Capture p50/p95 latency, cost, task success, invalid choices, confidence calibration and outage fallback. Promote Jev only if it earns a specific role.
4. Extend to a small human-facing Matrix scene only after fixture outcomes and runtime contracts are accepted. Measure PC and Quest 3 separately on real builds/devices; do not infer device readiness from a desktop fixture.

The first deliverable is a reproducible experiment and a go/no-go recommendation, not a promise of emergent civilization or a shipped NPC community.
